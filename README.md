##Запуск

Приложение запускается через Docker командой:
```bash
docker compose up --build
```

Поднимаются 2 контейнера с PostgreSQL (db) и непосредственно API (app). Миграции применяются при старте контейнера автоматически - docker compose подтягивает в контейнер app скрипт entrypoint.sh который накатывает миграции и стартует приложение. Настройки передаются через .env.example файл и подтягиваются как в код через PydenticSettings, так и в докер со скриптом. После старта приложения документация запросов доступна на: `http://127.0.0.1:8000/docs`.

Остановка:
```bash
docker compose down
```
Данные Postgres остаются в volume `postgres_data`.

P.S. Я знаю что .env файлы не должны попадать в git, а .env.example должен быть заполнен моковыми данными, но т.к. в .env.example для этого проета нет ни одного реального секрета, а только параметры настроек я его сохраню для быстроты и удобства развёртывания.

## Детали реализации

- Курсы НБРБ загружаются при старте и каждый день в 06:00. Добавил в lifespan планирование этой задачи, т.к. если проложение долго не перезапускать - ставки устареют. Ответ логируется. Повтор той же валюты на ту же дату не создаёт вторую строку - для этого прописано ограничение в модели и оно вызывается при сохранении ставок в `rates_repo`.
- `POST /deal/create` - сумма и две разные валюты. Коды приводятся к верхнему регистру. В ответе id сделки, сумма в целевой валюте и применённый курс. Нет курса - 404.
- `POST /deal/resolve` - `accept` переводит сделку в `completed`, `reject` в `failed`. Повторное решение - 409, неизвестный id - 404. Строка блокируется через `select_for_update` на время обновления, проставляется `resolved_at`.
- `GET /deal/pending` - список сделок в статусе `pending`.
- `GET /deal/stat` - статистика кассы за период. Даты в query как `dd.mm.yyyy`, день входит целиком. Валюта необязательна. Считаются только завершённые сделки (в статусе `completed`). Расчёты призводятся агрегационными функциями на стороне БД.
- BYN в таблицу курсов не пишется: для него курс `1` и scale `1`. Остальные валюты берутся из последних данных по ним. Кросс-курс идёт через белорусский рубль.
- В базе две таблицы: `rates` и `deals`. В таблице `deals` у сделки есть 3 статуса `pending` / `completed` / `failed`, время создания и проведения. Сделка сздаётся в статусе `pending`, в другие статусы её переводят по вызову `POST /deal/resolve`. Проверки: сумма и курс больше нуля, `resolved_at` не раньше `created_at`, остальная валидация проводится на уровне моделей. Дополнительные индексы не уместны т.к. запросов на создание и мзменение данных будет больше чем на чтение + на статусы нет смысла делать индесы т.к. слишком большая селективность - всё-равно Posgres пойдёт через seq_scan. Для `rates` индекс сформировался при написании `UniqueConstraint`.
- Лог пишется в консоль с уровня INFO и в файл с уровня WARNING, файл ротируется.
- Тесты: `uv sync --frozen --group dev`, затем `uv run pytest`. Перед коммитом запускаются pre-commit: ruff, mypy и базовые проверки файлов.
